# 2026-10-01 — Progress Log

## Milestone: "Removed Server 3 still shows in the bot" — last hard-coded server lists made dynamic

**Reported symptom:** Server 3 was deleted in the dashboard (Settings → Outline
Servers, only #1 and #2 remain), yet the Telegram bot still offered
"Server 3" — in the plan-purchase server picker and in old replacement-request
messages.

### Root cause
The 2026-09-30 fix made all *key-routing* paths (issuance, renew, replace,
notifier, stats) Settings-driven, but two display surfaces still had a
hard-coded 3-server list baked in:

1. `bot_app/handlers/shop.py` — `handle_select_plan` rendered three fixed
   buttons (`buywallet_{plan}_1/2/3`) regardless of the Settings store. This
   was the live bug behind the "Server 3 ဖြင့် ဝယ်မည်" screenshot.
2. `bot_app/services/reports.py` — `get_monthly_revenue_report` always printed
   exactly three server revenue rows and lumped every non-1/2/3 sale into VIP
   (a Settings-added Server 4's revenue was invisible as its own row).

The replacement-request screenshot ("Server 1 ကို / 2 / 3") shows a button
label format that no longer exists anywhere in git history — those are stale
messages sent by an older deployed build (old chats keep their old inline
keyboards; new requests already render dynamically per the 09-30 fix).

### Fix — Settings store as the single source of truth for display too
- `bot_app/services/outline.py`
  - New `clean_server_label()` + `get_server_display_name(server_id)`: reads
    the Settings server list, strips decoration emojis, falls back to
    `Server <id>` for ids missing from Settings (historical data of a removed
    server).
  - `get_servers_total_usage` now uses the shared helper (dedup).
- `bot_app/handlers/shop.py`
  - Plan-purchase server picker now renders **one button per configured
    server** (`📡 {Settings name} ဖြင့် ဝယ်မည်` → `buywallet_{plan}_{sid}`),
    so removing/renaming/adding servers in Settings updates the bot with no
    redeploy.
  - Success texts + admin purchase alert use the Settings server name instead
    of the hard-coded "Singapore Server N 🇸🇬".
  - Ultimate-VIP / redeem-credit flow stays pinned to Server 1 (intentional
    business rule), now with a dynamic label.
- `bot_app/services/reports.py`
  - Revenue rows are bucketed per server id from sales history, ordered by the
    Settings server list, then VIP, then legacy ids found in history (removed
    servers' past revenue stays visible, no phantom rows otherwise). Server-4
    sales now get their own row instead of being folded into VIP.
- `bot_app/handlers/menu.py` — replacement-request buttons reuse
  `get_server_display_name` (dedup, same behavior).
- `bot_app/handlers/points.py` — Points-redeem success text uses the dynamic
  Server-1 display name (issuance target unchanged, "1" by design).

### Deliberately untouched (correct by design)
- `settings.py` env-derived defaults and `outline.py` env-only fallbacks —
  they only fire when the Settings store is empty.
- Redeem-credit / Ultimate / Points keys issuing on Server 1 — business rule.

### Test run results
- `tests/test_dynamic_server_ui.py` (new — 9 tests): display-name resolution
  + emoji cleanup, plan buttons follow Settings (no ghost Server 3, S4
  appears, names from Settings, Ultimate pinned to S1), revenue rows follow
  Settings (legacy S3 row from history only, S4 no longer in VIP).
- **349 passing** (340 pre-existing + 9 new). Zero regressions.

### Operational notes for the owner
- Settings changes reach the bot within the settings cache TTL (**45 s**) —
  no redeploy needed.
- Old Telegram messages never re-render: replacement requests sent *before* a
  fix/deploy keep their old buttons. Verify with a **new** request.
- The replacement-request screenshot shows a label format absent from the
  whole git history → the live Vercel build is likely older than
  `e394a45` (2026-09-30). If a fresh replacement request still lists a removed
  server, redeploy main from the Vercel dashboard and re-test.
