## 🔌 Incident: prod bot deaf again — webhook re-pointed to site ROOT (fixed 08:2x MMT)

**User report**: bot on Vercel stopped responding to button presses (~08:11–08:16 MMT).
User suspected the local run (`npm install && npm run dev`, and/or `python index.py --mode hybrid`) broke it. Prod bot `@H_E_FEATURE_Bot` ☘️ (8779558815), local dev bot `@outlinekeydev_bot` (8864…, `BOT_MODE=polling`).

**Diagnosis (live probes)**:
- `getWebhookInfo` (prod): `url = https://outline-key-bot.vercel.app/` (ROOT — the exact bug fixed last night), `last_error = 405 Method Not Allowed` (root serves static `index.html`, rejects POST), `pending_update_count = 14` queued updates.
- Local dev bot `getWebhookInfo`: `url = ""` → the 08:08:49 MMT `index.py --mode hybrid` run (shell history) only touched the DEV token and its `remove_webhook()` was a no-op.
- Code audit: nothing in the repo can set a webhook except `scripts/set_webhook.py` and `index.py --mode webhook --webhook-url <url>`; neither ran with the prod token. `bot_app/helpers/webhook_guard.py` is read-only. `npm run dev` never touches Telegram.
- The 06:43 MMT notifications in the screenshot are OUTGOING sends (cron-triggered `sendMessage`) — those work even with a broken webhook; only the RECEIVING path was dead. So "worked this morning" ≠ webhook was healthy at 06:43.
- `/diag?key=sha256(TOKEN)[:16]` on the prod token returned full healthy payload (`git_sha=13fa902`, kv on, 2 Outline servers OK) → deployed Vercel env token is still the prod token.

**Root cause of the re-break**: NOT the local run. Something external re-ran `setWebhook` against the site ROOT between last night's verified `/webhook` fix and this morning (most likely BotFather `/setwebhook` with the domain without the `/webhook` path, or a manual curl). No local command in this repo's history could have done it.

**Fix (applied, verified)**:
`.venv/bin/python scripts/set_webhook.py reset --token <prod> --url https://outline-key-bot.vercel.app/webhook --drop-pending`
→ verified: `url=/webhook`, `pending=0`, no last_error, `callback_query` delivered; `POST /webhook` → `{"status":"ok"}`; `/diag` status ok.

**Answer to the user's question**: local runs did not cause it — different bot token, and local code only ever removes (never sets) webhooks on that token.

**Lessons / prevention**:
1. Whenever the webhook is (re)set, the URL MUST end in `/webhook` — root 405s once static output exists at `/`.
2. Quick health check anytime: `.venv/bin/python scripts/set_webhook.py check --token <prod> --url https://outline-key-bot.vercel.app/webhook`.
3. Outgoing notifications arriving ≠ webhook healthy (sends don't need a webhook); judge health by button-press replies or `getWebhookInfo`.
4. Local dev stays on the dev token (`@outlinekeydev_bot`); never paste the prod token into local `.env`.

## 🧾 Slip images 404 on Vercel: '%23' path segment not decoded (fixed, deployed 906d9e6)

**User report**: slips showed when testing locally, but the Vercel dashboard showed empty thumbnails and "Receipt Unavailable" in the lightbox.

**Diagnosis chain** (all live-probed):
1. KV seemed empty under `admin_slips_data` — actually stored under the LITERALLY-quoted key `"admin_slips_data"` because `kv.py` double-encodes: `quote(json.dumps(key))` bakes the JSON quotes into the Redis key name. Harmless (reads use the same encoding), but confusing for manual inspection.
2. Slip records ARE in KV (4 slips, all with prod-bot `file_id`s); prod token `getFile` resolves #082412's file (45 KB jpg) — backend data path healthy.
3. Local end-to-end run (real KV + prod token): image endpoint returns 200 JPEG — code correct.
4. Authed probe against PROD (TMA initData signed with the bot token for admin id — token-derived, no PIN needed): list endpoint 200 ✓, `/slips/%23082412/image` → **404 "Slip not found"** ⇒ the encoded `%23` reached the handler undecoded.

**Root cause**: browsers percent-encode `#082412` as `%23…`; Flask's own dev server decodes PATH_INFO per WSGI (why local worked), but on Vercel the rewrite destination `/api/index.py` gets its path restored by `VercelPathFixMiddleware` from `X-Matched-Path`/`X-Forwarded-Uri` — RAW and still-encoded. Werkzeug matched `<slip_id>` = literal `"%23082412"` → KV lookup miss → 404. Same defect silently broke slip **detail and Approve/Reject** on prod.

**Fix (commit `906d9e6`, deployed, verified)**:
- `VercelPathFixMiddleware`: percent-decode the forwarded path once when it still contains `%` (no double-decode of already-decoded paths).
- Slip endpoints (`detail`/`image`/`review`) defensively `unquote()` the id param.
- Regression tests: encoded-id through detail/image/review + 3 middleware unit tests. Suite **154/154**, pyflakes clean.
- Prod verification: image endpoint → 200 image/jpeg 45189 bytes; detail → slip JSON.

**Notes**:
- With the local `.env` now on the dev bot token, slips received by the PROD bot render only on the Vercel dashboard (Telegram file_ids are bot-specific — dev token getFile fails with 400). The user's "worked locally" memory predates the three-bot token cleanup.
- TMA initData for the admin id can be minted with the bot token for read-mostly diagnosis (verify function has no auth_date expiry check — consider adding one).
