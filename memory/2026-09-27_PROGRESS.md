3. Outgoing notifications arriving ≠ webhook healthy (sends don't need a webhook); judge health by button-press replies or `getWebhookInfo`.

## 🧾 Slip images 404 on Vercel: '%23' path segment not decoded (fixed, deployed 906d9e6)

**User report**: slips showed when testing locally, but the Vercel dashboard showed empty thumbnails and "Receipt Unavailable" in the lightbox.

**Diagnosis chain** (all live-probed):
1. KV seemed empty under `admin_slips_data` — actually stored under the LITERALLY-quoted key `"admin_slips_data"` because `kv.py` double-encodes: `quote(json.dumps(key))` bakes the JSON quotes into the Redis key name. Harmless (reads use the same encoding), but confusing for manual inspection.
2. Slip records ARE in KV (4 slips, all with prod-bot `file_id`s); prod token `getFile` resolves #082412's file (45 KB jpg) — backend data path healthy.
3. Local end-to-end run (real KV + prod token): image endpoint returns 200 JPEG — code correct.
4. Authed probe against PROD (TMA initData signed with the bot token for admin id — token-derived, no PIN needed): list endpoint 200 ✓, `/slips/%23082412/image` → **404 "Slip not found"** ⇒ the encoded `%23` reached the handler undecoded.

**Root cause**: browsers percent-encode `#082412` as `%23…`; Flask's own dev server decodes PATH_INFO per WSGI (why local worked), but on Vercel the rewrite destination `/api/index.py` gets its path restored by `VercelPathFixMiddleware` from `X-Matched-Path`/`X-Forwarded-Uri` — RAW and still-encoded. Werkzeug matched `<slip_id>` = literal `"%23082412"` → KV lookup miss → 404. Same defect silently broke slip **detail and Approve/Reject** on prod.

**Fix (commit `906d9e6`, deployed, verified)**:
- `VercelPathFixMiddleware`: percent-decode the forwarded path once when it still contains `%` (no double-decode of already-decoded paths).
- Slip endpoints (`detail`/`image`/`review`) defensively `unquote()` the id param.
- Regression tests: encoded-id through detail/image/review + 3 middleware unit tests. Suite **154/154**, pyflakes clean.
- Prod verification: image endpoint → 200 image/jpeg 45189 bytes; detail → slip JSON.

**Notes**:
- With the local `.env` now on the dev bot token, slips received by the PROD bot render only on the Vercel dashboard (Telegram file_ids are bot-specific — dev token getFile fails with 400). The user's "worked locally" memory predates the three-bot token cleanup.
- TMA initData for the admin id can be minted with the bot token for read-mostly diagnosis (verify function has no auth_date expiry check — consider adding one).

## 🐛 Critical: Upstash redis_set silently lost every write containing '/' (fixed, pushed)

**Found while verifying the Telegram-sync feature locally**: dashboard approve
succeeded but the admin message wasn't edited. The slip had been recorded by
old code (pre-restart), and re-testing then exposed a deeper bug.

**Root cause** ([bot_app/storage/kv.py](file:///home/zixuan/Projects/outline-key-bot/bot_app/storage/kv.py)):
`redis_set` sent the JSON value as a GET path segment via
`urllib.parse.quote(json.dumps(value))` — but quote's default `safe='/'`
leaves forward slashes intact, so any state blob containing a `/` (file_ids,
captions, URLs…) made Upstash reject the command with `ERR syntax error`
(HTTP 400). The `except`/status check swallowed it → **Upstash writes failed
silently while the /tmp file copy succeeded**, so prod (no writable /tmp
across instances) and the local server diverged without anyone noticing.

**Fix**: POST the value as the request body — `POST /set/<json-quoted-key>`
with `Content-Type: text/plain` (verified against the real Upstash instance
with tricky payloads: `/`, `+`, `=`, `#`, unicode). Regression tests in
[tests/test_kv_storage.py](file:///home/zixuan/Projects/outline-key-bot/tests/test_kv_storage.py)
(2 tests: value travels in body not URL; failure status propagates).

**E2E verified locally** (dev bot, real Telegram): slip recorded with
admin_messages → dashboard review → `editMessageCaption` landed
"✅ APPROVED (+12,345 MMK)" + button removed (confirmed via the
"message is not modified" response on re-edit). Test artifacts cleaned.

**Suite**: 168/168 (includes the parallel WIP's tests), pyflakes clean.

**Next**: confirm Vercel deploy picked this up (`/diag` git_sha); the same
silent-write-loss may have been affecting prod state sync since session
pooling landed — worth watching the dashboard after deploy.
