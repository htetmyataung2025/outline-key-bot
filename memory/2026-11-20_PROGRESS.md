## Bot update #13 — Support Chat photos (owner request)
- **Why**: customers must be able to show an error screenshot so support (owner or the Muse agent) can see it and answer.
- **Design**: Telegram hosts the images (free tier). `customer_say_photo()` forwards the photo to every admin via `send_photo` and stores the Telegram `file_id` in the thread (`type: "photo"`, caption in `text`). Nothing is stored when the photo reaches no admin, so the app can ask for a retry.
- **Endpoints** (`bot_app/routes_app.py`): `POST /api/app/support/send-photo` (bearer; base64 JSON, ≤3.5 MB decoded, caption ≤1000 chars, 10/min), `GET /api/app/support/photo?file_id=` (bearer) and `GET /api/app/support/agent/photo?file_id=` (agent secret) — both proxy bytes back from Telegram via `fetch_photo_bytes()` (`bot.get_file` + `bot.download_file`).
- **Admin → customer photos**: a new photo handler in `bot_app/handlers/menu.py` routes an admin's photo Reply on a forwarded message into the thread (`admin_reply_photo()`, counts as owner presence).
- **App side** (same v0.6.8 fix-round): attach button + photo picker (compress ≤1280 px JPEG), photo bubbles with tap-to-full-view, proxy fetch with an in-memory cache; support notifications show "📷 ပုံ ပို့ထားပါတယ်" for caption-less photos.
- **Tests**: BotStub gained send_photo/get_file/download_file; 3 new tests (forward+store, admin photo routing, endpoints incl. auth and bad-base64). Suite: **479 passed / 1 known pre-existing failure**.
- Files: `bot_app/services/support_chat.py`, `bot_app/routes_app.py`, `bot_app/handlers/menu.py`, `tests/test_support_chat.py`, this note.

## Bot Update #18 — Facebook promo keys via Support Chat (2026-11-20 ~19:40)

Owner is running a Facebook promo: customers who send the code `HEFREEFORYOU` in the in-app Support Chat get a free trial key from the support agent.

- **Service** (`bot_app/services/promo.py`, NEW): `claim_promo_key(chat_id, fallback_name)` — KV claims record `promo_claims:hefreeforyou` {chat_id: {ts, key_name, expire_date}}; a `redis_set_nx` lock serializes claims; one claim per account, hard cap 50. Creates the key via `create_outline_key("2", <profile full_name>, custom_gb=10, custom_days=5, is_giveaway=True)` — the key name ends with the expiry date so the nightly expiry cron auto-deletes it; `save_persistent_key` inside lands it in the customer's My Keys. Also writes a 0-Ks purchase record ("Free Promo (Facebook)") + key mapping + an app-inbox notification. A failed creation is NOT recorded, so the customer can retry with the code.
- **Endpoint** (`bot_app/routes_app.py`): `POST /api/app/support/agent/promo-key` (agent secret) {chat_id, code, name?} → 200 {ok, vpn_key, expire_date, ...} / 409 already_claimed|cap_reached|busy / 400 bad_code / 502 key_creation_failed. Code match is case-insensitive.
- **Agent rule** (support-auto-answer cron, updated the same day): a message containing the code goes through the promo flow before any other classification — an explicit exception to the "free-key requests are unsafe" rule; without the code, free-key requests still escalate.
- **Tests**: new `tests/test_promo.py` — 6 tests (secret required, bad code, success args: Server 2 / 10 GB / 5 days / giveaway / customer name, one-per-user, cap reached, failed creation not recorded). Suite: **495 passed / 1 known pre-existing failure**.

- **Agent rule** (support-auto-answer cron, updated the same day): promo replies now say the key is in Telegram DM + Profile → History "Free Promo" (tap → My Keys) and explicitly never claim it lands in My Keys by itself; the already-claimed branch re-sends the returned key.

## Bot Update #19 — slip auto-review agent (2026-11-20 ~20:50)

Owner's model (same as Support Chat): while he is present he reviews top-up slips himself; while he is away, a slip that has waited >3 minutes may be checked and approved by Muse — but only when every check clearly passes. Muse never rejects.

- **Service** (`bot_app/services/slips.py`): `pending_slips_for_agent()` — PENDING slips oldest-first, enriched with `tx_duplicate` computed across ALL slips (any status): a transaction reference seen more than once = a re-used slip, the most common top-up fraud.
- **Endpoints** (`bot_app/routes_app.py`, agent-secret guarded): `GET /api/app/agent/slips/pending` (returns `owner_present` + enriched slips), `GET /api/app/agent/slips/photo?file_id=` (same photo proxy as support), `POST /api/app/agent/slips/review` — refuses with 409 while `owner_present()`; otherwise calls the existing `review_slip` choke point with `reviewed_by="Claude Agent"` (wallet credit, points, audit log, admin-message badge and customer notifications all come from the choke point, identical to the owner's own approvals).
- **Checker** (new cron `slip-auto-review`, 1 min, goal h-e-vpn-app): skips slips younger than 3 min; downloads and views each slip photo; approves ONLY if receiver = 09699970092 / Htet Myat Aung, amount matches exactly, tx id present and not duplicate, slip date within 24 h before submission and not in the future, no visible edit signs, method not contradicted. Any doubt → slip stays PENDING and the owner gets ONE main-chat alert per slip (dedupe list in the goal's hidden_files). Approvals are silent in the main chat.
- **Tests**: new `tests/test_slip_agent.py` — 6 tests (secret required on all endpoints, pending enrichment + duplicate flag, 409 while owner present, approve credits the wallet + reviewed_by recorded + double-review refused, validation 400/404, photo endpoint). Suite: **504 passed / 1 known pre-existing failure**.
