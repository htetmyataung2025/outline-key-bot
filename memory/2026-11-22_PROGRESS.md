## Bot Update #20 — Slip amount auto-fill from OCR (pushed 2026-11-22 on the owner's instruction)

**#20.1 (added the same night, owner-approved):** the native-app and Mini App flows generated the Top-Up ID as a random 8-character string (the owner spotted `E1EACVR1` on the 2026-11-21 midday O Mar' Dee Dee slip and asked why it was not read from the receipt). Both flows now prefer the bot flow's transaction-derived ID (`#` + tx last-6) when OCR read a reference, falling back to the random ID when unreadable or already taken (a record is never overwritten). The app flow also records `extracted_tx_id` now, so the agent duplicate check covers app slips.

**Problem (owner-reported 2026-11-22 ~00:06):** many customers select the wrong top-up amount before uploading their slip (e.g. select 1,000 Ks, send a 5,000 Ks slip); the recorded slip amount was the *selected* one, so mismatches landed on the admin/owner to untangle (e.g. the 2026-11-21 O Mar' Dee Dee 500-vs-4,000 duplicate submissions).

**Fix:** at slip intake, the slip photo's OCR text is mined for the transfer amount; when one is confidently read it replaces the customer-selected amount on the recorded slip.

- `bot_app/services/ocr.py`
  - `extract_slip_amount(ocr_text)` — label-anchored first (amount labels EN/MM, value on the same or next line; "balance" lines never count), then currency-anchored (numbers next to Ks/MMK/ကျပ်, most-repeated wins). Token filter rejects dates, times, phone numbers and transaction references (comma/decimal/round + 100–1,000,000 Ks range).
  - `parse_slip_ocr_bytes(img_bytes)` — OCR.space base64 variant for flows that receive raw bytes.
  - `extract_slip_facts(file_path)` — ONE OCR pass returning `(order_id, tx_last6, amount)`; `extract_order_id_and_tx` now delegates to it (same signature/behaviour).
  - `extract_amount_and_tx_from_bytes(img_bytes)` — `(tx_last6, amount)` for byte-based flows.
  - `resolve_slip_amount(selected, detected)` — detected wins when ≥ 500 Ks; below that (or None) the selection stands and the slip is flagged for the admin.
- Intake wiring (all three channels): `bot_app/handlers/topup.py` (Telegram bot), `bot_app/routes_app.py` `POST /api/app/topup` (native app — also now records `extracted_tx_id`, previously always empty), `bot_app/routes_user.py` `POST /api/user/topup-slip` (Mini App).
  - Admin alert shows a 🤖 correction line when the amounts differ (selected → slip amount) or a ⚠️ "OCR could not read the amount" flag when it falls back; the Approve button, recorded amount and customer confirmation all use the final amount; the customer is told when their amount was corrected.
- `bot_app/services/slips.py` — `record_slip` accepts `ocr_amount` / `selected_amount` (stored on the record for audit); `pending_slips_for_agent()` exposes both so the slip auto-review agent can see them.

**Tests:** new `tests/test_slip_amount.py` (18 tests: parsing cases incl. KBZ/Wave receipts, balance-line guard, Myanmar digits, non-slip text; resolve rules; single-OCR-pass facts; app + Mini App endpoint auto-fill, fallback and ID collision). Two existing tests re-pointed to the new handler seam (`extract_slip_facts`). Full suite: **523 passed / 1 known pre-existing failure** (`test_user_api_bootstrap_new_user`, fails on pristine tree too).

**Status:** pushed via the GitHub connector on the owner's instruction 2026-11-22 ~00:24; Vercel auto-deploys from main. No app update needed; bot-side only. ## Bot Update #21 — Slip-photo gate (non-slip photos bounced at intake)

The owner re-raised this himself at 00:35 (after the earlier drop) and approved the build at 06:33, after a 25-second explainer video (~/workspace/your_files/slip-gate-explainer/). Motivating case: SanPhyoWin's 2026-11-21 install-screen screenshots submitted as top-up slips.

**Gate (`bot_app/services/ocr.py`):** `slip_photo_is_probable(ocr_text)` — True when the OCR text shows ANY sign of a real wallet receipt: a transaction reference, a transfer amount, the shop's receiving phone/name, or a wallet brand marker (KBZ/Wave/AYA/CB/UAB/OnePay). Deliberately generous — a photo is bounced only when NOTHING slip-like is found, so genuine-but-blurry receipts still pass. `extract_slip_facts` now returns a 4-tuple `(order_id, tx_last6, amount, probable)` and `extract_amount_and_tx_from_bytes` a 3-tuple `(tx_last6, amount, probable)` — still one OCR pass per photo.

**Channels:**
- **Telegram bot:** a bounced photo is parked via the new `slip_gate_state` (services/states.py + `SLIP_GATE_STATE_FILE`) and the customer gets `NOT_A_SLIP_NOTICE_BOT` with one inline button "✅ ပြေစာ အစစ်ပါ — Admin စစ်ပေးဖို့ ပို့မယ်" (`slip_gate_send` callback). Tapping it runs the shared `_finalize_topup_slip()` with `unverified=True`. Nothing is recorded and no admin alert is sent for a bounced photo.
- **Native app / Mini App:** bounced with HTTP 400 `{success: False, error: "not_a_slip", message: NOT_A_SLIP_MESSAGE}` before any admin alert/record. A caller that vouches for the photo (`force_slip`) gets it recorded flagged instead.
- Forced slips: `record_slip(..., unverified_photo=True)` stores the flag, the admin alert carries a ⚠️ "စစ်ဆေးရန် လိုသည်" note, and `pending_slips_for_agent()` exposes `unverified_photo` so the auto-review agent can treat them as human-only.

**Tests:** new `tests/test_slip_gate.py` (13 tests: verdict cases, bot bounce + escape hatch + no-state noop, app bounce/force, Mini App bounce/force). Existing mocks updated for the wider tuples (`test_slip_amount.py`, `test_admin_api_slips.py`, `test_admin_action_audits.py`, `test_user_api_actions.py`). Full suite: **536 passed / 1 known pre-existing failure**.

**Status:** pushed via the GitHub connector on the owner's instruction 2026-11-22; bot-side only, no app update.
