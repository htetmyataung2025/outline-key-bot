# 2026-09-30 — Progress Log

## Milestone: Server 4 routing bug — root-caused & fixed

**Reported symptom:** issuing a key from "Server 4" (added via the Settings page)
created the key on Server 3's Outline host instead.

### Root cause
Every key issuance / lookup / search path resolved the Outline API URL via a
hard-coded ternary that clamped any id other than `1`/`2` to Server 3:

```python
api_url = OUTLINE_API_URL_1 if str(server_num) == "1" else (OUTLINE_API_URL_2 if str(server_num) == "2" else OUTLINE_API_URL_3)
```

Because `OUTLINE_API_URL_4` doesn't exist in `bot_app/config.py` and none of the
functions consulted the dynamic Settings store, Server 4 silently fell into the
`else` branch and hit Server 3.

### Fix — single source of truth: dynamic settings with env fallback

Added two helpers in `bot_app/services/outline.py`:

- `resolve_server_api_url(server_id)` — looks up the server in the dynamic
  Settings store first (`get_configured_servers`); falls back to the legacy
  `.env` slots (`OUTLINE_API_URL_1/2/3`) only for ids 1-3 when no Settings
  server matches. Returns `""` for unconfigured ids (no silent fall-through).
- `server_num_for_api_url(api_url)` — reverse-maps a URL back to a server id,
  used by `fetch_key_from_server` so the correct server number is reported.
- `iter_configured_server_urls()` — yields every configured server URL.
  Settings servers take priority; env slots are used **only** when the Settings
  store is empty (env-only deployments). This avoids duplicate probes when the
  prod host is saved differently in Settings vs `.env`.

- `bot_app/services/outline.py`
  - Replaced all 4 ternary chains (`create_outline_key`,
    `renew_specific_unlimited_key`, `renew_or_create_unlimited_key`,
    `get_user_ultimate_keys`, `fetch_key_from_server`) with
    `resolve_server_api_url` / `server_num_for_api_url`.
  - `get_servers_total_usage` — now iterates dynamic servers; legacy 3-server
    text preserved as fallback when no Settings rows exist.
  - `get_customer_summary_stats` — per-server user counts are now driven by the

  - `search_users_by_query` — probes dynamic servers for live key search.
  - `get_user_next_key_number` — next-key-number probe uses dynamic servers.
- `bot_app/services/notifier.py`
  - Expiry cron loop now uses `iter_configured_server_urls()` instead of the
    hard-coded `[OUTLINE_API_URL_1..3]` triple, so Server 4 keys are
    expiry-checked too.
- `bot_app/handlers/admin.py`
  - `viewkey_` and `ask_send_key_` handlers resolve URLs via
    `resolve_server_api_url`.
- `bot_app/handlers/keys.py`
  - Key-replacement delete uses `resolve_server_api_url` for the old server.
- `bot_app/handlers/menu.py`
  - Replacement-request and paste-key flows now probe **all** configured
    servers (so a Server-4-pasted key is found) instead of only S1/S2/S3.
  - Replace-to buttons are generated dynamically for every configured server
    (S1/S2/S3/S4 …) rather than the hard-coded 3 buttons — clicking

  - Pinned the server list via a `get_system_settings` stub so the cron tests

- `tests/test_server_routing.py` (new — 8 regression tests)
  - `resolve_server_api_url("4")` → Server 4 URL.
  - `create_outline_key("4", …)` POSTs to the Server-4 host (not Server 3).
  - Unknown server id → no Outline call (no silent fallback).
  - `iter_configured_server_urls` yields S4; env fallback only fires when
    Settings is empty.

### Repro used to confirm the bug (and verify the fix)
A standalone script monkeypatched `requests.post` and called `create_outline_key`
for ids 1/2/3/4 against env-loaded URLs:

| before fix | POST landed on |
|---|---|
| 1 | ✅ server 1 |
| 2 | ✅ server 2 |
| 3 | ✅ server 3 |
| 4 | ❌ server 3 |

After the fix, `create_outline_key("4", …)` POSTs to Server 4's host and
persists the key under server `"4"` in the registry.

### Known issues / caveats
- Server 4 was already saved in the prod KV Settings store (`Server 4 🇮🇳`),
  so no new env var is needed — it is picked up automatically now.
- `config.py` still defines only `OUTLINE_API_URL_1/2/3`. Servers 4+ must be
  added through the Settings page (the supported configuration surface). If
  desired, an `OUTLINE_API_URL_4` env var could be wired into
  `settings._get_default_settings`, but that was intentionally left out to keep
  configuration in one place (Settings).
- The notifier cron now scans Server 4 too; if Server 4 is expected to be
  excluded from nightly expiry scans, it should be removed from the Settings
  server list rather than coded around.
